# Грабли 2.3

## Запустил все num_threads потоков, включая последний

В диапазоне не больше элементов, чем нужно; `main` сам выполняет роль одного
«потока». Если создать `num_threads` потоков, один блок останется необработанным
(или будет обработан дважды). Запускай `num_threads - 1`, последний блок считает
`main`.

## Передал `results[i]` без `std::ref`

Конструктор `std::thread` копирует аргументы — поток обновил бы копию, а
`results[i]` остался бы нулём. Обязательно `std::ref(results[i])`.

## Забыл про остаток от деления

`block_size = length / num_threads` отбрасывает остаток. Последний блок (`block_start..last`)
должен идти до конца диапазона и захватывать хвост — нельзя останавливаться
на `first + num_threads * block_size`.

## Не ограничил число потоков

Если создать поток на каждый элемент или не огрaничить `max_threads`, получишь
сотни потоков, и переключения контекста убьют производительность. Всегда
`min(hardware, max_threads)`.

## Использовал `unsigned` вместо `unsigned long` в формулах

На 32-битных платформах `unsigned` может не вместить `length` для больших
векторов. Формулы с `unsigned long` безопаснее. Смешение типов даёт warning
с `-Wall -Wextra` — следи за ним.

## Ожидал, что для float результат совпадёт с accumulate

Не ассоциативная арифметика: порядок сложения меняется при разбиении на блоки.
Для `int`/`long long` совпадение точное, для `float`/`double` — не гарантировано.

## Прочитал `results` до join()

Если суммировать `results` до `join()`, потоки могут ещё писать — данные гонки
за `results[i]` и неверный итог. Сначала все `join()`, потом финальный
`accumulate`.
