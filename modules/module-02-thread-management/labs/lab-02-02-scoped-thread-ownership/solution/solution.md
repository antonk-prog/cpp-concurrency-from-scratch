# Решение 2.2

## scoped_thread — владеющая RAII-обёртка

```cpp
class scoped_thread {
public:
    explicit scoped_thread(std::thread t_) : t(std::move(t_)) {}
    scoped_thread(const scoped_thread&) = delete;
    scoped_thread& operator=(const scoped_thread&) = delete;
    ~scoped_thread() {
        if (t.joinable()) {
            t.join();
        }
    }
private:
    std::thread t;
};
```

Разбор:

- **Конструктор** принимает `std::thread` по значению и перемещает его в член
  `t`. Параметр по значению уже означает «я забрал владение у вызывающего»
  (для этого в вызове и нужен `std::move` или временный объект). `explicit`
  защищает от неявных преобразований.
- **Копирование запрещено** (`= delete`): две копии обёртки попытались бы
  `join()` один и тот же поток — а `join()` можно вызвать только один раз.
  В отличие от `thread_guard` (который хранил `std::thread&`), здесь поток
  принадлежит обёртке, поэтому ссылочной проблемы времени жизни нет.
- **Деструктор** проверяет `joinable()` и зовёт `join()` — поток гарантированно
  завершится до конца области видимости, в том числе при исключениях.

## Возврат std::thread из функции

```cpp
std::thread makeWorker(int value) {
    return std::thread(doWork, value);
}
```

Временный `std::thread` перемещается в вызывающего — владение потоком уходит
наружу без копирования. Затем `makeWorker(7)` передаётся прямо в конструктор
`scoped_thread` (тоже временный объект — перемещение неявное).

## Почему владение надёжнее ссылки

`thread_guard` (из лабы 1.3) хранит `std::thread&` — сам поток живёт в `main`,
и обёртка лишь «приглядывает» за ним. Если объект `thread_guard` переживёт
переменную потока или его скопируют, гарантии рушатся. `scoped_thread` владеет
потоком напрямую: никто другой не может его `join()`/`detach()` после передачи
в обёртку, а завершение гарантировано самим классом.
