# Модуль 2. Управление потоками

## Лекция

### Зачем это нужно

В главе 1 мы запустили поток, передали ему аргументы и просто дождались его
через `join()`. Реальный код требует большего: уметь передать потоку аргументы
безопасно и гибко, решить — ждать его завершения
или отпустить в фон, передать право владения потоком другой функции, запустить
группу потоков для разбиения работы, а иногда — отличить один поток от другого.
Всё это — управление потоками, и стандартная библиотека даёт для этого объект
`std::thread`. Управление потоком сводится к ответам на четыре вопроса:
какой код он выполняет, какими данными пользуется, кто за него отвечает и как
его отличить от других.

### Как это работает

У каждой программы есть минимум один поток — тот, что выполняет `main()`,
а новые потоки запускаются созданием объекта `std::thread`, которому передаётся
задача. Задача — это любой вызываемый объект: обычная функция, функтор
(класс с `operator()`), лямбда или указатель на член класса.

Важный момент: при передаче функционального объекта конструктор
`std::thread` **копирует** его в хранилище, принадлежащее новому потоку, и вызывает
оттуда. Поэтому копия должна вести себя точно так же, как оригинал. Если функтор
содержит изменяемое состояние или ссылки, это может привести к неожиданностям —
например, два потока получат не то состояние, которое ожидалось.

Конструктор `std::thread` **копирует** переданные аргументы в хранилище, которым
владеет поток, а затем вызывает целевую функцию, передавая эти копии как
rvalue-значения (как будто это временные объекты). Из-за этого есть три важных
следствия, на которые стоит обратить особое внимание:

1. **Ссылку нужно оборачивать в `std::ref`.** Конструктор копирует аргументы,
   не обращая внимания на тип параметра функции. Если функция ждёт `int&`,
   а передать `data`, поток получит копию и функция обновит копию, а не оригинал.
   Обёртка `std::reference_wrapper` из `std::ref(data)` проносит настоящую ссылку
   сквозь копирование.

2. **Move-only типы — через `std::move`.** Типы, которые нельзя скопировать
   (например, `std::unique_ptr`), передаются только перемещением. Передавая
   именованный объект, нужно явно обернуть его в `std::move(p)`, чтобы право
   владения перешло в поток.

3. **Указатель на буфер может «прожить» меньше, чем нужно.** Когда вы передаёте
   `char const*` в функцию, которая ждёт `std::string`, важно понимать:
   конструктор `std::thread` ничего не знает о типе параметра функции. Он не
   станет превращать `char const*` в `std::string` при создании потока — он
   просто сохранит указатель. Преобразование в `std::string` произойдёт позже,
   внутри потока, уже при вызове функции. И если исходный буфер к тому моменту
   будет уничтожен (например, это локальная переменная, а поток отсоединён через
   `detach()`), то `std::string` будет сконструирован из указателя на
   освобождённую память — это неопределённое поведение. Поэтому строки надёжнее
   приводить к `std::string` **до** передачи в поток, пока буфер ещё жив. Это
   классическая ловушка: «конструктор `std::thread` копирует аргументы как есть,
   не преобразуя их в ожидаемый тип».

   ```cpp
   void print(std::string s) {
       std::cout << s << "\n";
   }

   int main() {
       {
           char buf[6] = "hello";      // локальный буфер на стеке
           std::thread t(print, buf);  // сохраняется char* на buf
           t.detach();                 // поток отсоединён
       }                               // <-- buf уничтожен здесь!
       // поток где-то в этот момент делает: std::string(ptr)
       // ptr указывает на мёртвую память → UB
   }
   ```

Поток, запущенный с `std::thread`, надо явно **присоединить** (`join()`) или
**отсоединить** (`detach()`) до уничтожения объекта. Если этого не сделать,
деструктор `std::thread` у ещё «присоединяемого» (joinable) потока вызовет
`std::terminate()`. `std::terminate()` — аварийное завершение программы: это
«последний рубеж» библиотеки, когда она не может разрешить ситуацию сама.
Решение нужно принимать до уничтожения объекта, даже если сам поток давно
завершился: после завершения поток всё равно остаётся joinable, пока не вызван
`join()`/`detach()`. Это правило нужно соблюдать и при исключениях — надёжнее
всего через RAII-обёртку.

Про `join()` стоит знать две вещи. Во-первых, вызвать его можно **только один
раз**: после `join()` объект `std::thread` больше не связан ни с одним потоком,
и `joinable()` возвращает `false`. Во-вторых, `join()` также освобождает
системное хранилище, связанное с завершённым потоком. Если нужно более тонкое
ожидание (с проверкой или ограничением по времени) — это уже условные переменные
и фьючерсы из главы 4.

**Проблема времени жизни.** Если не ждать завершения потока, нужно убедиться,
что данные, к которым он обращается, живы, пока он с ними работает. Классический
пример ([листинг 2.1](#листинг-21-функция-возвращающая-управление-пока-поток-держит-ссылку-на-локальную-переменную)):
функция запускает поток, который держит ссылку на её
локальную переменную, и отсоединяет его. Функция выходит — локальная переменная
уничтожается, а поток продолжает писать по висячей ссылке:

#### Листинг 2.1. Функция, возвращающая управление, пока поток держит ссылку на локальную переменную

```cpp
void do_something(int& i) { ++i; }

struct Worker {
    int& target;
    explicit Worker(int& t) : target(t) {}
    void operator()() const {
        for (int j = 0; j < 1000000; ++j) do_something(target);
    }
};

void oops() {
    int local_state = 0;
    std::thread t(Worker(local_state));
    t.detach();          // поток живёт после выхода из oops
}                        // local_state уже уничтожен → обращение по ссылке = UB
```

Это неопределённое поведение. Обрати внимание: это та же ошибка, что
и в однопоточном коде (сохранить указатель на локальную переменную после выхода
из функции), но в многопоточном коде её гораздо легче допустить, а проявляется
она не сразу. Лечится двумя способами: сделать функцию потока автономной
(скопировать данные в поток) или гарантированно дождаться потока до выхода
из функции.

**Владение потоком.** `std::thread` нельзя копировать, но можно **перемещать** —
как и другие типы, владеющие ресурсом (`std::unique_ptr`, `std::ifstream`).
В любой момент с конкретным потоком связан ровно один объект `std::thread`,
и это право владения можно передавать между объектами. Это позволяет:
возвращать `std::thread` из функции, принимать его в функции по значению,
хранить потоки в контейнерах и строить владеющие RAII-обёртки. Если
переместить поток в объект, который уже связан с другим потоком, старый поток
«потеряется» — деструктор снова вызовет `std::terminate()` (то же правило,
что и для обычного уничтожения).

Перемещение бывает явным и неявным. Именованный объект нужно перемещать явно —
`std::move(t)`; временный объект перемещается сам, автоматически. Это же
правило действует, когда поток передаётся в функцию по значению:

```cpp
void f(std::thread t);           // принимает владение
f(std::thread(work));            // временный — неявное перемещение
std::thread t(work);
f(std::move(t));                 // именованный — явное перемещение
```

Владеющие RAII-обёртки (`scoped_thread`) строятся как раз на этом: они берут
`std::thread` в конструкторе, прячут его внутри и присоединяют в деструкторе —
так что поток невозможно «потерять» или присоединить дважды.

### Минимальные примеры

**Запуск с разными вызываемыми объектами.** Функция, функтор, лямбда:

```cpp
void work() { /* ... */ }

struct Worker {
    void operator()() const { /* ... */ }
};

std::thread t1(work);                 // функция
std::thread t2(Worker{});             // функтор
std::thread t3([] { /* ... */ });     // лямбда
t1.join(); t2.join(); t3.join();
```

**Осторожно, «самый неприятный случай синтаксического анализа»:**

```cpp
std::thread t(Worker());   // компилятор видит ОБЪЯВЛЕНИЕ функции t,
                           // а не переменную! Функция, которая принимает
                           // указатель на функцию и возвращает std::thread.
```

Компилятор интерпретирует это как объявление функции, а не как создание потока.
Исправление — дополнительные скобки или фигурные скобки:

```cpp
std::thread t((Worker()));   // ok
std::thread t{Worker()};     // ok
```

Ещё один способ задать задачу — **указатель на член класса** вместе с объектом:
конструктор вызывает этот метод на переданном экземпляре:

```cpp
class Task {
public:
    void run(int v) { /* ... */ }
};

Task task;
std::thread t(&Task::run, &task, 42);   // вызовет task.run(42) в новом потоке
t.join();
```

Лямбда избавляет от «самого неприятного случая синтаксического анализа»: она
всегда считается объектом, поэтому `std::thread t([]{ /* ... */ });` — всегда
создание потока, а не объявление функции.

**Передача аргументов.** По ссылке — через `std::ref`, move-only — через
`std::move`:

```cpp
void accumulate(int n, int& out) { out += n; }
void consume(std::unique_ptr<int> p) { /* ... */ }

int result = 0;
std::thread t1(accumulate, 42, std::ref(result));   // ссылка на result
std::unique_ptr<int> data = std::make_unique<int>(7);
std::thread t2(consume, std::move(data));            // владение уходит в поток
t1.join();
t2.join();
```

**Владеющая RAII-обёртка.** Гарантирует `join()` при любом исходе. Простая
версия хранит ссылку (`thread_guard`), владеющая — сам поток (`scoped_thread`):

```cpp
class scoped_thread {
    std::thread t;
public:
    explicit scoped_thread(std::thread t_) : t(std::move(t_)) {}
    scoped_thread(const scoped_thread&) = delete;
    scoped_thread& operator=(const scoped_thread&) = delete;
    ~scoped_thread() { if (t.joinable()) t.join(); }
};
```

Владеющая версия надёжнее: поток спрятан внутри обёртки, никто не может его
«потерять» или присоединить повторно. В C++17 такое
`scoped_thread` в стандарт не вошло (предложение `joining_thread` отклонили),
но класс легко написать самому — мы и делаем это в лаборатории.

Поток можно вернуть из функции — право владения перемещается наружу:

```cpp
std::thread make_worker() {
    return std::thread([] { /* ... */ });
}
```

**Группа потоков.** `std::vector<std::thread>` — удобный способ запустить
несколько потоков и дождаться их всех:

```cpp
std::vector<std::thread> threads;
for (unsigned i = 0; i < 20; ++i) {
    threads.push_back(std::thread(do_work, i));
}
for (auto& t : threads) t.join();
```

Вектор «соберёт» потоки, а цикл `join()` дождётся каждого. Такой приём —
основа разбиения работы между потоками.

**Выбор числа потоков.** `std::thread::hardware_concurrency()` возвращает
подсказку о числе аппаратных потоков (может вернуть 0, если неизвестно):

```cpp
unsigned n = std::thread::hardware_concurrency();
unsigned threads = n ? n : 2;   // на 0 берём разумный запас
```

Не запускай больше потоков, чем есть аппаратных: лишние потоки
создают переключения контекста и снижают производительность. Но и слишком мало
потоков плохо — не используется доступная конкурентность.

В главе 2 есть показательный пример использования всего этого вместе —
параллельный `std::accumulate` ([листинг 2.8](#листинг-28-параллельный-stdaccumulate)). Полный код — в репозитории
`ccia_code_samples/listings/listing_2.8.cpp`; здесь — сокращённая версия:

#### Листинг 2.8. Параллельный std::accumulate

```cpp
template <typename Iterator, typename T>
T parallel_accumulate(Iterator first, Iterator last, T init) {
    const unsigned long length = std::distance(first, last);
    if (!length) return init;

    const unsigned long min_per_thread = 25;
    const unsigned long max_threads =
        (length + min_per_thread - 1) / min_per_thread;
    const unsigned long hardware =
        std::thread::hardware_concurrency();
    const unsigned long num_threads =
        std::min(hardware != 0 ? hardware : 2ul, max_threads);
    const unsigned long block_size = length / num_threads;

    std::vector<T> results(num_threads);
    std::vector<std::thread> threads(num_threads - 1);

    Iterator block_start = first;
    for (unsigned long i = 0; i < num_threads - 1; ++i) {
        Iterator block_end = block_start;
        std::advance(block_end, block_size);
        threads[i] = std::thread(accumulate_block<Iterator, T>(),
                                 block_start, block_end,
                                 std::ref(results[i]));
        block_start = block_end;
    }
    accumulate_block<Iterator, T>()(block_start, last,
                                    results[num_threads - 1]);
    for (auto& t : threads) t.join();
    return std::accumulate(results.begin(), results.end(), init);
}
```

Логика такая:

- длина диапазона делится на блоки; `min_per_thread = 25` — минимальное число
  элементов на поток, чтобы не плодить потоки ради пяти значений;
- число потоков = `min(hardware_concurrency(), max_threads)`, где `max_threads`
  выведено из длины; на 0 от `hardware_concurrency()` берут 2;
- запускается `num_threads - 1` потоков (сам `main` — «ещё один»), каждый
  считает свой блок и пишет результат в свою ячейку через `std::ref`;
- последний блок (включая «хвост» от деления с остатком) считает главный поток;
- все потоки `join()`-ятся, частичные результаты складываются.

Важный вывод: результат `parallel_accumulate` для `float`/`double` может
отличаться от однопоточного `std::accumulate` — порядок сложения меняется,
а арифметика с плавающей точкой неассоциативна. Для целых типов совпадение
точное. В лаборатории 2.3 мы напишем эту функцию сами.

**Идентификация потоков.** У каждого потока есть идентификатор типа
`std::thread::id`. Его получают двумя способами: из объекта — `t.get_id()`,
изнутри самого потока — `std::this_thread::get_id()`. У объекта без связанного
потока `get_id()` возвращает значение «не поток» (созданный по умолчанию id).
Идентификаторы можно копировать и сравнивать; равны они тогда и только тогда,
когда представляют один и тот же поток (или оба — «не поток»). Есть полный
набор операторов сравнения и `std::hash<std::thread::id>`, поэтому id можно
использовать как ключи в (упорядоченных и неупорядоченных) ассоциативных
контейнерах. Типичное применение — проверить, выполняет ли текущий поток
особую «главную» роль:

```cpp
std::thread::id master_thread;

void some_core_part() {
    if (std::this_thread::get_id() == master_thread) {
        /* работа, доступная только главному потоку */
    }
    /* общая работа */
}
```

Идентификаторы полезны, когда нужно привязать к потоку данные или поведение
в глубине стека вызовов, куда не хочется пробрасывать индекс вручную. Отметим
нюанс: `std::thread::id` не несёт семантической нагрузки — это просто
уникальный «номер». Если вывести его в `std::cout`, конкретная строка зависит
от реализации; стандарт гарантирует лишь, что равные id печатаются одинаково,
а разные — по-разному. Для отладки и журналирования этого достаточно.

### Типичные ошибки

**«Самый неприятный случай синтаксического анализа»** — `std::thread t(Worker());`
объявляет функцию, а не создаёт поток. Используй `{ }` или лишние скобки.

**Забыл `join()`/`detach()`** — joinable-поток в деструкторе вызывает
`std::terminate()` (аварийное завершение программы). Обязательно реши судьбу
потока до конца его области видимости, в том числе при исключениях (для этого —
RAII-обёртка).

**Вызвал `join()` дважды или на не-joinable потоке** — `join()` можно вызывать
только один раз и только у joinable-потока; повторный вызов — ошибка
(`std::system_error`). Перед `join()` проверяй `t.joinable()`.

**Ссылка на локальную переменную в detached-потоке** — если поток отсоединён
и обращается к локальной переменной функции, а функция уже вышла, переменная
уничтожена → UB. Либо жди поток до выхода из функции, либо копируй данные
в поток.

**Передал ссылку без `std::ref`** — поток получил копию, функция обновила её,
оригинал не изменился. Компиляция может даже упасть (нельзя передать rvalue
в `int&`).

**Надеялся на неявное преобразование аргумента** — передал `char const*`
в функцию, ждущую `std::string`: преобразование происходит уже в потоке, и если
буфер умрёт раньше — UB. Приводи к целевому типу до передачи.

**Скопировал `std::thread`** — `std::thread` не копируется (удалён конструктор
копии). Перемещай через `std::move` или создавай временный объект.

**Создал больше потоков, чем ядер** — лишние переключения контекста съедают
выигрыш. Ограничивай число потоков `hardware_concurrency()`.

**Пишет в `std::cout` из нескольких потоков** — вывод перемешивается, порядок
строк не гарантирован. Собирай результаты в потоках, а печатай из `main` после
`join()`.

### Шпаргалка

| Что | Как | Смысл |
|-----|-----|-------|
| Запуск потока | `std::thread t(fn, args...)` | поток начинает с `fn(args...)` |
| Ожидание | `t.join()` | ждёт завершения; вызывается один раз |
| Отсоединение | `t.detach()` | поток живёт в фоне, объект теряет связь |
| Проверка | `t.joinable()` | true, пока не вызван join/detach |
| Ссылка-аргумент | `std::ref(x)` | проносит настоящую ссылку через копирование |
| Move-only | `std::move(x)` | передаёт владение в поток |
| Перемещение потока | `std::thread t2 = std::move(t1)` | передача владения потоком |
| Возврат потока | `return std::thread(fn);` | владение уходит из функции |
| Группа потоков | `std::vector<std::thread>` | запустить много и дождаться всех |
| Текущий поток | `std::this_thread::get_id()` | id текущего потока |
| id потока | `t.get_id()` | id потока объекта `t` |
| Число потоков | `std::thread::hardware_concurrency()` | подсказка о числе аппаратных потоков |
| RAII-обёртка | `thread_guard`/`scoped_thread` | гарантированный `join()` при любом исходе |
