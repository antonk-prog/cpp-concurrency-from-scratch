# Решение лабы 10.1

## Реализация

**`combine_visits`** — комбинирующий функтор, покрывающий все четыре
комбинации операндов, которые может использовать `transform_reduce`:
карта + карта, запись лога + карта, карта + запись лога, запись + запись.

«Карта + карта» сводится по меньшей из двух карт: если левая меньше правой,
они меняются местами, и обходится `rhs` (теперь меньшая). Так мы делаем
меньше операций вставки и копирования ключей — для миллионов записей это
заметно.

Остальные три перегрузки просто инкрементируют счётчик страницы в карте
(или заводят новую карту для двух записей).

**`count_visits_per_page`** — один вызов `transform_reduce`:

```cpp
return std::transform_reduce(
    std::execution::par, lines.begin(), lines.end(),
    visit_map_type(), combine_visits(), parse_log_line);
```

Аргументы: политика, диапазон, начальное значение, операция сведения,
функция преобразования. `parse_log_line` превращает строку в `log_info`,
`combine_visits` объединяет результаты. Библиотека вправе обрабатывать
элементы блоками и комбинировать в любом порядке — поэтому так важны все
четыре перегрузки `combine_visits`.

## Почему нет гонок

`transform_reduce` разбивает диапазон на блоки; каждый поток накапливает
собственную локальную карту и только потом они объединяются. Общих изменяемых
структур в лямбде/функторе нет — гонки за данные невозможны. Именно поэтому
подходит `par`, а не `for_each` с общим `unordered_map` (там понадобился бы
мьютекс на каждую вставку).

## Проверка

Программа генерирует 200 000 строк лога, считает посещения через
`transform_reduce(par)` и сверяет с эталонным последовательным подсчётом.
Результат совпадает: `pages = 5`, `result = OK`, exit 0. TSan чист.
(На машинах без TBB политика `par` выполняется последовательно — корректность
от этого не меняется.)
