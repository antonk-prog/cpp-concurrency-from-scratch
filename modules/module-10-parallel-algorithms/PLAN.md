# Модуль 10 — Алгоритмы параллельных вычислений — ПЛАН

## Допущения модуля

### Прогрессия (что разрешено)
- Всё из модулей 1–9. Ключевые опоры: `std::atomic`, мьютексы (м3–5),
  `std::reduce`/`accumulate` (м2), параллельные алгоритмы «вручную» (м8).
- Новое: политики выполнения `std::execution::{seq,par,par_unseq}`
  (C++17, `<execution>`) и параллельные переопределения алгоритмов
  (`transform_reduce`, `for_each`, `sort` и т.д.) — тема модуля 10.
- Запрещено всё из C++20+: `std::jthread`, `std::counting_semaphore`,
  `std::barrier`, `std::latch`, корутины, `std::format`.
- Ограничение среды: на целевых/проверочных машинах без TBB
  (`libtbb-dev`) политики `par`/`par_unseq` выполняются последовательно
  (libstdc++ требует TBB для настоящего параллелизма). Поэтому лабы
  модуля строятся на СЕМАНТИКЕ политик и корректности результата, а не на
  измерении ускорения. Решение пользователя 2026-09-09.
- При сборке достаточно `g++ -std=c++17 -pthread` (без `-ltbb`);
  код компилируется и корректно работает при последовательном fallback.

### Тематика (соответствие главе 10)
Лекция покрывает:
- 10.1 Зачем: параллельные переопределения алгоритмов, `par` как «разрешение,
  не требование», изменение сложности;
- 10.2 Политики выполнения:
  - классы и объекты политик (`sequenced_policy`/`parallel_policy`/
    `parallel_unsequenced_policy`, объекты `seq`/`par`/`par_unseq`, `<execution>`);
  - 10.2.1 общие последствия: сложность (ослабление до O(...)), поведение при
    исключении (`std::terminate`; только `bad_alloc`), где/когда выполняются
    операции;
  - 10.2.2 `sequenced_policy`: один поток, без перемежения, но порядок
    НЕ определён (пример `x = ++count`);
  - 10.2.3 `parallel_policy`: несколько потоков, операции упорядочены в
    пределах потока; требования (без гонок, без зависимости от потока);
    примеры `++x` vs `x = ++count` (UB), атомарность как «легальная», но
    бессмысленная синхронизация;
  - 10.2.4 `parallel_unsequenced_policy`: перемежение, перенос операций между
    потоками; ЗАПРЕТ любой синхронизации (мьютексов, атомарных переменных);
  - 10.3 Список параллельных алгоритмов: почти все `<algorithm>`/`<numeric>`;
    `accumulate` не распараллеливается, `reduce` — его параллельный
    контрпартнер (неассоциативность, недетерминизм результата);
    требования к категориям итераторов: input/output запрещены, нужны forward
    (пример `std::copy`);
  - 10.3.1 Примеры: параллельный цикл `for_each(par)`, выбор политики
    (по умолчанию `par`; `par_unseq` — только без синхронизации);
    листинги 10.1 (X с внутренним мьютексом: `par` ок, `par_unseq` — UB)
    и 10.2 (Y без синхронизации + `ProtectedY`: `par_unseq` ок);
  - 10.3.2 Подсчёт посещений: `transform_reduce` (листинг 10.3),
    `combine_visits`.

### Список лаб (тип, название, суть, чему учит)

1. **lab-10-01-transform-reduce (напиши с нуля, средняя)**
   - Суть: реализовать подсчёт посещений страниц из лога через
     `std::transform_reduce(std::execution::par, ...)` (листинг 10.3):
     парсер строки и комбинирующий функтор; результат сравнить с эталонным
     последовательным подсчётом.
   - Чему учит: `transform_reduce` (map+reduce в одной функции), комбинирующий
     функтор, почему результат корректен при любом порядке сведения.
   - Прогрессия: политики выполнения (м10), `std::unordered_map` (STL),
     `std::reduce`-идея (м2/м8).

2. **lab-10-02-seq-order (предскажи вывод, средняя)**
   - Суть: `std::for_each(std::execution::seq, ...)` с `x = ++count`.
     Предсказать, гарантирован ли порядок заполнения (1..N), сравнить
     с `std::for_each` без политики.
   - Чему учит: политика `seq` ≠ «обычный» алгоритм: порядок не
     специфицирован, даже без распараллеливания; сложность и исключения
     тоже меняются.
   - Прогрессия: `for_each` (STL), политики (м10).

3. **lab-10-03-policy-exceptions (предскажи вывод, средняя)**
   - Суть: программа с двумя режимами (флаг `--policy`): без политики
     исключение из лямбды перехватывается try/catch; с `std::execution::seq` —
     `std::terminate`. Предсказать вывод в обоих режимах и объяснить, почему
     `seq` «не даёт» перехватить исключение.
   - Чему учит: исключения с политиками выполнения: terminate, допустимо
     только `bad_alloc`; принципиальное отличие `seq` от вызова без политики.
   - Прогрессия: исключения (C++), политики (м10).

## Заголовки лекции (README.md) с 1–2 фразами содержания

1. **Зачем это нужно** — распараллеливание «в одну строку», политики как
   разрешение, а не требование; цена (сложность, исключения).
2. **Политики выполнения (10.2)** — три класса и три объекта, `<execution>`,
   нельзя создавать свои политики.
3. **Общие последствия (10.2.1)** — сложность, исключения (`terminate`,
   только `bad_alloc`), где/когда выполняются операции.
4. **sequenced_policy (10.2.2)** — один поток, без перемежения, но порядок
   неопределён; пример `x = ++count`.
5. **parallel_policy (10.2.3)** — несколько потоков, требования (без гонок,
   без зависимости от потока); `++x` ок, `x = ++count` — UB; атомарность
   легальна, но убивает смысл.
6. **parallel_unsequenced_policy (10.2.4)** — перемежение, перенос между
   потоками; запрет любой синхронизации.
7. **Параллельные алгоритмы (10.3)** — список; `accumulate` vs `reduce`
   (неассоциативность, недетерминизм); категории итераторов (input/output
   запрещены, forward обязателен; пример `copy`).
8. **Примеры (10.3.1)** — `for_each(par)`; выбор политики; листинги 10.1
   (внутренний мьютекс: par ок, par_unseq UB) и 10.2 (без синхронизации:
   par_unseq ок).
9. **Подсчёт посещений (10.3.2)** — `transform_reduce`, комбинирующий
   функтор (листинг 10.3).
10. **Типичные ошибки** — общий счётчик с `par`; порядок с `seq`; мьютекс
    с `par_unseq`; `accumulate` вместо `reduce`; input-итераторы.
11. **Шпаргалка** — таблица: политика, требования, когда использовать.
