# Решение лабы 8.2

## Ошибка

Флаг остановки `done_flag` объявлен как обычный `bool`. Его читают все
рабочие потоки в цикле (`!*done_flag`), а пишет тот поток, который нашёл
соответствие (`*done_flag = true`). Одновременные чтение и запись неатомарной
переменной из разных потоков без синхронизации — гонка за данные (UB).
Программа могла «работать», потому что планировщик не сводил потоки в
опасный момент, но это чистая случайность.

## Исправление

Флаг становится `std::atomic<bool>`, а доступ к нему — через `load()` и
`store(true)`:

```cpp
std::promise<Iterator> result;
std::atomic<bool> done_flag(false);
```

```cpp
for (; begin != end && !done_flag->load(); ++begin) {
    if (*begin == match) {
        result->set_value(begin);
        done_flag->store(true);
        return;
    }
}
```

Параметр `find_element` меняется на `std::atomic<bool>* done_flag`. В
`catch`-блоке тоже `done_flag->store(true)`. После объединения потоков
проверка «нашлось ли» — `done_flag.load()`.

`std::atomic<bool>` использует `memory_order_seq_cst` по умолчанию: чтение
флага видит запись других потоков (общий порядок), этого достаточно.

## Проверка

Стартер (неатомарный `bool`) под TSan: прогон 300 поисков по массиву из
200 000 элементов, искомое — первый элемент (потоки гарантированно
перекрываются) → TSan ловит гонку за `done_flag`.

Решение под TSan: чисто. Программа печатает `found = 0 at 0`, результат `OK`,
exit 0. Ранняя остановка работает: потоки прекращают проверку, как только
флаг установлен.

## Замечание про «гонку за promise»

Если соответствие найдут несколько потоков почти одновременно, первый
выиграет `set_value`, остальные получат исключение от `promise::set_value`
(состояние уже установлено). Это не гонка за данные: `std::promise`
потокобезопасен. Поэтому в `catch (...)` мы и перехватываем всё, включая этот
случай, и результат остаётся корректным.
