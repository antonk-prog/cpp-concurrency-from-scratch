# Лаба 8.3. Конкуренция за общий счётчик
Модуль: 8. Разработка конкурентного кода
Тип: нагрузочный вопрос

## Мотивация

Самый наивный способ «распараллелить» суммирование — общий атомарный
счётчик, который все потоки увеличивают вместе. Код прост, но на большой
нагрузке он работает медленнее однопоточного: каждый `fetch_add` требует
«свежую» строку кэша, и она курсирует между ядрами. Это конкуренция при
обращении к данным — один из главных факторов деградации из раздела 8.2.

## Задача

Дан бенчмарк с общим атомарным счётчиком: один поток увеличивает его
`threads * n` раз, `threads` потоков — по `n` раз каждый (суммарно поровну).

1. Собери и запусти стартовый код. **Предскажи и объясни**, какой режим
   быстрее: один поток или несколько потоков с общим счётчиком. Проверь
   предсказание измерением.
2. Объясни, почему на маленьком числе итераций разница почти не видна, а на
   большом (100 млн на поток) общий счётчик проигрывает в десятки раз.
3. **Почини** программу: дай каждому потоку собственный счётчик (выровненный
   через `std::hardware_destructive_interference_size`), измерь улучшение.

Объясни письменно (что происходит, почему, как починка помогает).

## Требования

1. Объяснено, что такое конкуренция за данные и почему общий счётчик
   проигрывает на большой нагрузке.
2. В решении каждый поток увеличивает собственный счётчик, выровненный по
   `std::hardware_destructive_interference_size` (отдельная строка кэша).
3. Суммарный объём работы в сравниваемых режимах одинаков.
4. Код компилируется без предупреждений; TSan чист; программа печатает
   времена и завершается успешно (exit 0).

## Стартовый код

Файлы: `starter/main.cpp`.

Сборка и запуск:

```
g++ -std=c++17 -pthread -O2 -Wall -Wextra main.cpp -o counter_contention
./counter_contention
```

Обрати внимание: сборка с `-O2` — иначе эффект не проявится.
