# Грабли лабы 8.1

## Забыл присоединить потоки

Если `f` бросает исключение и функция выходит до цикла `join`, объекты
`std::thread` уничтожаются без `join`/`detach` — `std::terminate`. Решение —
RAII-обёртка `join_threads`, созданная сразу после вектора потоков.

## Породил поток с копией задачи вместо move

`std::packaged_task` не допускает копирования. В `std::thread` он передаётся
только через `std::move(task)`. Копирование — ошибка компиляции (это хорошо:
ошибку видно сразу).

## Обработал все блоки в потоках, а последний забыл

Последний блок обязан обработать текущий поток, иначе часть элементов останется
необработанной. Диапазон `[block_start, last)` — после цикла.

## Разделил диапазон не на смежные блоки

Если блоки перемежаются, соседние элементы обрабатывают разные потоки —
ложное совместное использование памяти и медленнее работа. Режем подряд.

## Не проверил пустой диапазон

При `length == 0` деление на `num_threads` и `std::advance` могут дать
некорректные итераторы. Сначала проверь `!length`.

## Посчитал `num_threads` больше, чем блоков

`max_threads = (length + min_per_thread - 1) / min_per_thread` ограничивает
число потоков числом блоков; без него при малом диапазоне может появиться
блок с нулевой длиной или лишние потоки.

## Считал, что `get()` не нужен, если исключений «не будет»

`futures[i].get()` обязателен: он и ждёт завершения задачи, и повторно выдаёт
исключение из рабочего потока. Без него исключение молча проглотится.

## Проверял только «по поведению», без TSan

Логические гонки (например, если два потока обрабатывают пересекающиеся
блоки) коварны. Прогони `-fsanitize=thread` и убедись, что он чист.
