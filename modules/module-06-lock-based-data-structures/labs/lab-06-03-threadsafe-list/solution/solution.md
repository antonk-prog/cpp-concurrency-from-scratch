# Решение лабы 6.3

## Ключевые идеи

**Мьютекс на каждый узел.** У каждого узла свой `std::mutex m`. Операция
удерживает блокировку только тех узлов, которые её интересуют, и снимает
блокировку по мере продвижения. Это позволяет разным потокам работать с разными
узлами одновременно.

**Эстафетная блокировка.** Обход всегда начинается с фиктивной головы `head`
и движется в одном направлении. Перед переходом к следующему узлу его мьютекс
блокируется, затем блокировка текущего снимается. Владение блокировкой
передаётся перемещением `unique_lock`:

```cpp
std::unique_lock<std::mutex> next_lk(next->m);
lk.unlock();
f(*next->data);
current = next;
lk = std::move(next_lk);
```

Так удерживается ровно одна блокировка, но узел, с которым работаем, всегда
защищён.

**`push_front`.** Узел создаётся и данные размещаются **вне** блокировки (дорогие
операции). Под `head.m` выполняется только обновление двух указателей — быстро
и безопасно.

**`find_first_if`.** Как `for_each`, но при `p(*next->data)` возвращается
`next->data` (`shared_ptr`) — данные остаются живыми, даже если узел потом удалят
из списка.

**`remove_if`.** Когда предикат истинен, узел удаляется переносом владения
в локальный `old_next` (`std::unique_ptr<node>`), который уничтожит узел при
выходе из области видимости. `current` не сдвигается — на место удалённого узла
встаёт следующий (`current->next = std::move(next->next)`), и его нужно проверить.

## Почему удаление после `next_lk.unlock()` безопасно

Удаляемый узел уничтожается **после** снятия его блокировки. Мьютекс
уничтожаемого узла никто не может захватить: до него можно добраться только
через `current->next`, а мьютекс `current` (`lk`) всё ещё удерживается. Значит,
ни один поток не может «застрять» на блокировке узла, который в этот момент
уничтожается (уничтожение заблокированного мьютекса — UB; здесь оно исключено).

## Почему нет deadlock

Итерация всегда идёт в одном направлении и всегда блокирует следующий узел,
прежде чем разблокировать текущий. Порядок блокировок жёстко фиксирован
(голова → следующий → следующий), поэтому цикла ожидания возникнуть не может.

## Ограничения

- Функции/предикаты выполняются под блокировкой узла — пользователь не должен
  вызывать из них операции списка (риск deadlock), а сам список не должен
  хранить ссылки наружу (иначе гонка).
- Потоки не обгоняют друг друга: если один поток долго обрабатывает узел,
  другие, дошедшие до этого узла, ждут.

4 писателя добавляют 20000 элементов; 4 потока параллельно обходят список
(каждый видит все 20000 — сумма и счётчик сходятся); `find_first_if` находит
существующий элемент и не находит отсутствующий; `remove_if` очищает список.
TSan чист.
