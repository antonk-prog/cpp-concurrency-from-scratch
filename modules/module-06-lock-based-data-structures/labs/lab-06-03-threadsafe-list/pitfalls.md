# Грабли лабы 6.3

## Забыл про `std::move(next_lk)` при передаче блокировки

Владельцем блокировки следующего узла должен стать `lk` (для продолжения цикла).
Без `lk = std::move(next_lk)` блокировка снимутся, и следующий узел окажется
незащищённым. `unique_lock` — move-only: передача владения — перемещением.

## Разблокировал текущий узел до блокировки следующего

Схема «заблокировать `next`, потом разблокировать `current`» обязательна.
Если сначала разблокировать `current`, а потом брать `next` — другой поток может
удалить `next` (он достижим через `current->next`, а `current` уже не защищён).

## В `remove_if` сдвинул `current` после удаления

Если после удаления узла сделать `current = next`, следующий за удалённым узел
будет пропущен (или проверен с нарушением блокировок). После удаления `current`
остаётся на месте — проверяется новый `current->next`.

## Уничтожил узел, пока его мьютекс заблокирован

Уничтожение заблокированного `std::mutex` — неопределённое поведение. Удаляемый
узел должен выйти из области видимости после снятия его блокировки. При этом
`current` (предыдущий узел) обязан оставаться заблокированным — иначе новый поток
может попытаться захватить мьютекс уничтожаемого узла.

## Вернул ссылку/значение на внутренние данные наружу

`find_first_if` возвращает `shared_ptr<T>`, а не `T&` или `T*`: копия `shared_ptr`
оставляет данные живыми даже после удаления узла. Возврат ссылки на `*next->data`
нарушил бы защиту (доступ без блокировки).

## Проверял только «по поведению» без TSan

Прогони `-fsanitize=thread`: решение должно быть чистым. Гонки в эстафетной
блокировке коварны — на глаз их не видно.
