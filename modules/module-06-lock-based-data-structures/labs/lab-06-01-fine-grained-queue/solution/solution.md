# Решение лабы 6.1

## Ошибка

В `pop_head()` поле `tail` читалось напрямую:

```cpp
if (head.get() == tail) {   // <-- tail без tail_mutex
```

`push()` пишет `tail` под `tail_mutex`. Когда `pop_head()` (в другом потоке)
читает `tail` без `tail_mutex`, это **гонка за данные** — неопределённое
поведение по модели памяти (глава 5). На практике гонка может «не проявляться»
долгое время, но она остаётся серьёзным багом.

## Исправление

Всё чтение `tail` выносится под `tail_mutex` — в отдельную функцию `get_tail()`:

```cpp
node* get_tail() {
    std::lock_guard<std::mutex> tail_lock(tail_mutex);
    return tail;
}
```

А в `pop_head()` прямое чтение заменяется вызовом `get_tail()`:

```cpp
std::unique_ptr<node> pop_head() {
    std::lock_guard<std::mutex> head_lock(head_mutex);
    if (head.get() == get_tail()) {   // get_tail() под head_mutex
        return nullptr;
    }
    ...
}
```

## Почему get_tail() обязан вызываться под head_mutex

Если бы `get_tail()` вызывался **до** захвата `head_mutex`, поток мог бы
«застрять» между чтением `tail` и блокировкой `head_mutex`: другие потоки
успели бы изменить и `head`, и `tail`. Возвращённый узел перестал бы быть
хвостовым и мог даже выпасть из списка. Тогда сравнение `head.get() == old_tail`
дало бы ложный результат, и при обновлении `head` можно было бы «увести» его
за актуальный `tail` — разрушив структуру.

Под `head_mutex` этого не происходит: никто не может изменить `head`, а `tail`
только продвигается вперёд по мере добавления узлов, поэтому `head` никогда
не перескочит за значение, возвращённое `get_tail()`.

## Порядок блокировок

Единственное место двух блокировок — `pop_head()`: всегда `head_mutex`, затем
`tail_mutex` (через `get_tail()`). Порядок фиксирован, значит, взаимная
блокировка невозможна.

## Проверка

С `-fsanitize=thread`:
- стартовый код ловит data race на `tail`;
- решение — чисто, все элементы извлечены (`consumed == total`).
