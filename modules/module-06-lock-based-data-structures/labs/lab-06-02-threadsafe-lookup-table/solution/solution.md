# Решение лабы 6.2

## Реализация

Все три метода следуют одному образцу: взять блокировку, найти запись по ключу,
выполнить действие. Изменяющие методы используют готовый `find_entry_for(key)`;
`value_for` (он `const`) делает поиск аналогично через `std::find_if` по
`const`-данным.

**`value_for`** — чтение, поэтому `shared_lock`: несколько читателей одного
сегмента работают параллельно. Если запись не найдена — возвращается
`default_value`, иначе — `found_entry->second`.

**`add_or_update_mapping`** — запись, поэтому `unique_lock`: если ключа нет —
добавляется пара, если есть — обновляется значение. Объединение «добавить/обновить»
в одну операцию устраняет гонку интерфейса (два потока не могут «вставить по
одному ключу» одновременно: первый вставит, второй обновит).

**`remove_mapping`** — запись, `unique_lock`: при наличии ключа — `erase`.

## Почему `value_for` — `const`, но блокирует `shared_mutex`

Метод объявлен `const`, потому что не меняет логическое состояние бакета. Но
блокировка — техническая операция, невидимая снаружи, поэтому мьютекс объявлен
`mutable` (тот же приём, что в главе 3).

## Почему shared_mutex на каждый сегмент

- Читатели одного сегмента не сериализуются (в отличие от `std::mutex`).
- Писатель в один сегмент не мешает операциям в других сегментах: ключ
  попадает в сегмент детерминированно через `hasher(key) % buckets.size()`,
  поэтому `get_bucket()` вызывается без блокировки.
- Конкурентность растёт с числом сегментов.

## Исключения

- `value_for` данные не меняет — безопасна.
- `remove_mapping` использует `erase`, который не бросает, — безопасна.
- `add_or_update_mapping`: `push_back` безопасен (при исключении список
  не меняется); обновление `it->second = value` может бросить, если бросает
  пользовательский оператор присваивания — это ответственность типа `Value`.

## Проверка

С `-fsanitize=thread` решение чисто. 4 писателя пишут 40000 ключей, 4 читателя
параллельно читают и проверяют — все значения корректны, TSan не находит гонок.
