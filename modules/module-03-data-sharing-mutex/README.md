# Модуль 3. Совместное использование данных несколькими потоками

## Лекция

### Зачем это нужно

Потоки в одном процессе разделяют адресное пространство — это их главное
преимущество: обмен данными между ними дёшев и прост. Но у медали есть обратная
сторона. Если два потока одновременно меняют одни и те же данные, результат
зависит от того, кто успел первым — это **состояние гонки** (race condition).
Гонка за данными (data race), когда один поток пишет, а другой читает тот же
объект без синхронизации, — это неопределённое поведение (UB). Программа может
работать годами и сломаться в самый неподходящий момент.

Главная защита от гонок за разделяемые данные в C++ — **мьютекс** (mutex,
mutual exclusion): примитив, который гарантирует, что в один момент времени
к защищаемым данным обращается только один поток.

### Как это работает

**Инварианты.** Разделяемая структура данных обычно имеет инварианты —
утверждения, верные в «спокойные» моменты. Например, в двусвязном списке
«если из узла A пройти вперёд к B, то из B назад попадёшь в A». Обновление
часто временно нарушает инвариант (меняем одну ссылку, потом вторую). Если
в этот момент другой поток прочитает структуру — увидит поломанное состояние.
Задача синхронизации — сделать так, чтобы никто не видел промежуточное состояние.

**Мьютекс и RAII.** Поток вызывает `lock()` перед доступом к данным и `unlock()`
после. Пока один поток держит блокировку, остальные ждут. Но прямые
`lock()`/`unlock()` опасны: при исключении `unlock()` можно пропустить. Поэтому
в C++ есть RAII-обёртки — `std::lock_guard`, которые блокируют мьютекс в
конструкторе и разблокируют в деструкторе:

```cpp
std::mutex m;
int shared_counter = 0;

void increment() {
    std::lock_guard<std::mutex> guard(m);   // m заблокирован
    ++shared_counter;                        // здесь безопасно
}                                            // guard разблокирует m
```

Данные и мьютекс принято держать вместе, в одном классе, а все методы, которые
трогают данные, — блокировать мьютекс. Так видно, какой код имеет доступ к данным.
Это сильный акцент: защита данных — это не просто «добавить
`lock_guard` в каждый метод». Важно, чтобы ни один метод не **выпускал** ссылку
или указатель на защищённые данные наружу (через возвращаемое значение, выходной
параметр или вызов неконтролируемой пользовательской функции). Одна «утечка»
ссылки за пределы блокировки — и любой код с этой ссылкой обращается к данным
без мьютекса, защита рушится полностью ([листинг 3.2](#листинг-32-случайная-передача-за-пределы-защиты-ссылки-на-защищаемые-данные)):

#### Листинг 3.2. Случайная передача за пределы защиты ссылки на защищаемые данные

```cpp
class data_wrapper {
    some_data data;
    std::mutex m;
public:
    template <typename Function>
    void process_data(Function func) {
        std::lock_guard<std::mutex> l(m);
        func(data);              // вызываем пользовательский код под блокировкой
    }
};

some_data* unprotected;

void malicious_function(some_data& protected_data) {
    unprotected = &protected_data;   // сохранил ссылку на защищённые данные!
}

void foo() {
    data_wrapper x;
    x.process_data(malicious_function);  // «безопасный» вызов…
    unprotected->do_something();         // …а дальше доступ БЕЗ блокировки
}
```

Здесь `process_data` выглядит безопасным, но переданный пользователем функтор
сохранил ссылку на защищённые данные, и дальше к ним обращаются без мьютекса.
Правило прямое: не передавай указатели и ссылки на защищённые
данные за пределы блокировки — ни через возвращаемое значение, ни через
сохранение во внешней памяти, ни через аргументы пользовательских функций.

**Интерфейсные гонки.** Мьютекс внутри класса не спасает от гонок, заложенных
в самом интерфейсе. Классика — `std::stack` с раздельными `empty()`/`top()`/`pop()`:

```cpp
if (!s.empty()) {      // в этот момент стек непуст
    int v = s.top();   // но другой поток мог вытолкнуть последний элемент
    s.pop();
}
```

Между `empty()` и `top()` другой поток может опустошить стек → `top()` на пустом
стеке — UB. А между `top()` и `pop()` два потока могут взять одно и то же
значение и потерять другое. Подчеркнём: даже если все методы стека
защищены мьютексом, гонка остаётся — она заложена в **интерфейсе** из раздельных
вызовов, а не в реализации. Решение — перепроектировать интерфейс: единая
операция, которая и читает, и удаляет под одним мьютексом. Такой стек мы
разберём в разделе «Минимальные примеры» ниже. Возврат через `shared_ptr` — не
случайность: он копируется без исключений, поэтому элемент не «теряется», если
копирование значения бросит `std::bad_alloc` в момент, когда элемент уже удалён
из стека.

**Deadlock.** Если операция требует двух мьютексов, потоки могут блокировать их
в разном порядке и намертво ждать друг друга: каждый держит один и ждёт второй.
Такой цикл ожидания называется **взаимной блокировкой** (deadlock). Типичный
сценарий — `swap` двух объектов: поток 1 блокирует `lhs.m`, поток 2 — `rhs.m`,
и каждый ждёт мьютекс, который держит другой.

Решение — блокировать оба мьютекса **одной операцией** — `std::lock(m1, m2, ...)`.
Его алгоритм устроен так, что поток никогда не остаётся в состоянии «один
мьютекс захвачен, второй жду»: если какой-то мьютекс из набора недоступен,
`std::lock` освобождает уже захваченные и ждёт весь набор целиком. Поэтому
два потока с переставленными аргументами не могут создать цикл ожидания.

В C++17 то же самое делает `std::scoped_lock` — RAII-обёртка над `std::lock`:
блокирует все переданные мьютексы в конструкторе, разблокирует в деструкторе
(даже при исключении):

```cpp
std::scoped_lock guard(lhs.m, rhs.m);   // блокирует оба без deadlock
```

До C++17 (или когда `scoped_lock` по какой-то причине не подходит) тот же приём
записывали так: `std::lock(lhs.m, rhs.m)` блокирует оба мьютекса, а
`lock_guard`-обёртки с флагом `std::adopt_lock` берут на себя разблокировку уже
захваченных мьютексов (флаг «adopt» означает «прими уже захваченную блокировку»):

```cpp
std::mutex m1, m2;

void swap_data(Data& a, Data& b) {
    std::lock(m1, m2);                                   // блокирует оба без deadlock
    std::lock_guard<std::mutex> g1(m1, std::adopt_lock); // «усыновили» захваченный m1
    std::lock_guard<std::mutex> g2(m2, std::adopt_lock); // «усыновили» захваченный m2
    // под обеими блокировками безопасно меняем a и b
}
```

`adopt_lock` лишь поручает RAII-обёртке разблокировать мьютекс, который уже
захвачен вызывающим кодом. В C++17 предпочтителен `scoped_lock` — он делает
то же самое одной строкой.

Важно: при обмене с одним и тем же объектом (`swap(x, x)`) блокировать мьютекс
дважды нельзя — это UB (для этого нужен `recursive_mutex`, см. ниже). Поэтому
перед блокировкой проверяют `&lhs == &rhs`.

**Гибкие блокировки.** `std::unique_lock` — как `lock_guard`, но с дополнительной
гибкостью: он не обязан владеть мьютексом с момента создания. Ему можно передать
флаг `std::defer_lock` — тогда конструктор мьютекс НЕ блокирует, и блокировку
можно взять позже явным `lock()`. Это нужно, например, чтобы передать
`unique_lock`-объекты в `std::lock` (они умеют перенаправлять блокировку на
свой мьютекс). Дальше блокировку можно снять раньше времени (`unlock()`), чтобы
не держать мьютекс во время долгих операций, и даже передать владение блокировкой
другой области видимости. Узнать, владеет ли `unique_lock` мьютексом, можно
через `owns_lock()`. Минус гибкости — `unique_lock` чуть больше и медленнее
`lock_guard`, поэтому там, где достаточно `lock_guard`, предпочитают его.

Пример: блокировка берётся явно, снимается раньше времени и берётся снова:

```cpp
std::mutex m;
int shared_data = 0;

void worker() {
    std::unique_lock<std::mutex> lk(m, std::defer_lock); // мьютекс пока НЕ блокирован
    // подготовка, не требующая блокировки
    lk.lock();                  // взяли блокировку явно
    ++shared_data;              // доступ к общим данным под мьютексом
    lk.unlock();                // сняли блокировку раньше времени
    // долгие операции — без удержания мьютекса
    lk.lock();                  // при необходимости блокировку берут снова
    bool held = lk.owns_lock(); // true, пока держим мьютекс
}
```

Комбинация `defer_lock` + `std::lock` блокирует два `unique_lock` атомарно,
без deadlock:

```cpp
std::unique_lock<std::mutex> lk1(m1, std::defer_lock);
std::unique_lock<std::mutex> lk2(m2, std::defer_lock);
std::lock(lk1, lk2);   // блокирует оба мьютекса за одну операцию
```

**Детализация блокировки.** Мьютекс защищает данные в течение времени удержания.
Два вопроса определяют эффективность: *сколько* данных защищает мьютекс и *как
долго* он удержан. Держать блокировку дольше, чем нужно, — плохо: остальные
потоки ждут. Блокируй мьютекс только на время реального
доступа к общим данным, а долгие операции (ввод-вывод, тяжёлые вычисления)
выполнять вне блокировки. Если защищать одним глобальным мьютексом все данные
программы, потоки выстроятся в очередь даже там, где могли бы работать
параллельно, — выигрыш от конкурентности сведётся к нулю. Если же детализация
слишком мелкая (мьютекс на каждый узел списка), приходится блокировать сразу
несколько мьютексов — а это путь к deadlock.

**Рекомендации против deadlock.** Кроме `std::scoped_lock`, есть набор
правил, которые снижают риск взаимных блокировок и там, где блокировки не
удаётся захватить одной операцией:

- **не вкладывай блокировки** — не захватывай второй мьютекс, пока держишь
  первый (если только не через `std::lock`/`scoped_lock`);
- **не вызывай пользовательский код, держа блокировку** — неизвестно, не
  попытается ли он снова взять мьютекс;
- **захватывай мьютексы в фиксированном порядке** — если операции всё же
  нужны две блокировки, все потоки должны брать их в одном и том же порядке;
- **используй иерархию блокировок** — каждому мьютексу назначается уровень,
  и поток может захватить мьютекс, только если его уровень ниже текущего.
  Нарушение иерархии обнаруживается сразу (исключением), а не редким зависанием.

Эти правила — самодисциплина: библиотека не может их проверить, но следование
им резко снижает вероятность взаимных блокировок.

**Альтернативы.** Мьютекс — не единственный инструмент защиты. Рассмотрим случаи,
где он избыточен или неудобен.

*Однократная инициализация.* Если данные нужно создать только один раз (открыть
соединение, выделить дорогой ресурс), а потом только читать, блокировать мьютекс
при каждом обращении — расточительно. Для этого есть `std::once_flag` (метка
«инициализация ещё не выполнена») и `std::call_once(flag, fn)`. `std::call_once`
гарантирует: каким бы потоком ни был вызван, `fn` выполнится ровно один раз,
а все остальные потоки будут ждать завершения инициализации и после неё увидят
готовые данные. Итог — потокобезопасная ленивая инициализация без постоянной
блокировки:

```cpp
std::shared_ptr<Resource> resource;
std::once_flag resource_flag;

void init_resource() { resource = std::make_shared<Resource>(); }

void use_resource() {
    std::call_once(resource_flag, init_resource);  // инициализирует один раз
    resource->do_something();
}
```

Тот же эффект для одной локальной переменной даёт `static`:
инициализация `static` локального объекта в C++11 и новее потокобезопасна —
она выполняется в одном потоке, а остальные ждут её завершения:

```cpp
Resource& get_resource() {
    static Resource r;   // создаётся один раз, потокобезопасно
    return r;
}
```

*Редко обновляемые данные.* Если данные часто читаются и редко обновляются
(кэш DNS, таблица конфигурации), обычный `std::mutex` заставит читателей
ждать друг друга — конкурентности чтения не будет. Для этого есть
`std::shared_mutex`: он допускает **два режима блокировки** — монопольный
(exclusive, один писатель) и общий (shared, много читателей одновременно).
Читатели берут общую блокировку через `std::shared_lock`, писатель — монопольную
через `lock_guard`/`unique_lock`. Пока есть хоть один читатель, писатель ждёт;
пока пишет писатель, читатели ждут. Так чтения идут параллельно, а обновления
остаются эксклюзивными:

```cpp
class dns_cache {
    std::map<std::string, Entry> entries_;
    mutable std::shared_mutex m_;
public:
    Entry find(const std::string& name) const {
        std::shared_lock<std::shared_mutex> l(m_);  // общая блокировка
        auto it = entries_.find(name);
        return it == entries_.end() ? Entry{} : it->second;
    }
    void update(const std::string& name, const Entry& e) {
        std::lock_guard<std::shared_mutex> l(m_);   // монопольная блокировка
        entries_[name] = e;
    }
};
```

*Рекурсивная блокировка.* `std::recursive_mutex` позволяет одному и тому же
потоку блокировать мьютекс несколько раз подряд (нужно столько же раз вызвать
`unlock`). Это пригодится, если метод класса, который уже держит мьютекс,
вызывает другой метод, тоже его блокирующий. Но рекурсивный мьютекс — обычно
сигнал плохой конструкции: пока держится блокировка, инварианты могут быть
нарушены. Лучше вынести общий код в приватный метод, который не блокирует
мьютекс, и вызывать его из блокирующих публичных методов.

Оговорка по `shared_mutex`: он не панацея. Выигрыш от
параллельных чтений появляется только при подходящем соотношении читателей
и писателей и достаточном числе ядер; накладные расходы `shared_lock` выше, чем
у обычного `lock_guard`. Поэтому выбор между `std::mutex` и `std::shared_mutex`
стоит подтверждать профилированием на целевой системе.

### Минимальные примеры

#### Листинг 3.1. Защищённый счётчик

```cpp
class Counter {
    int value_ = 0;
    mutable std::mutex m_;   // mutable — чтобы блокировать в const-методах
public:
    void increment() { std::lock_guard<std::mutex> g(m_); ++value_; }
    int get() const { std::lock_guard<std::mutex> g(m_); return value_; }
};
```

Обрати внимание на `mutable` у мьютекса. Метод `get() const` не меняет логическое
состояние счётчика, но блокировка мьютекса — техническая операция, не видимая
снаружи. Ключевое слово `mutable` разрешает менять поле в `const`-методе, поэтому
мьютекс можно блокировать даже в константных методах.

#### Листинг 3.5. Потокобезопасный стек

```cpp
struct empty_stack : std::exception { const char* what() const noexcept override {
    return "empty stack"; } };

template <typename T>
class threadsafe_stack {
    std::stack<T> data_;
    mutable std::mutex m_;
public:
    void push(T v) { std::lock_guard<std::mutex> g(m_); data_.push(v); }
    std::shared_ptr<T> pop() {
        std::lock_guard<std::mutex> g(m_);
        if (data_.empty()) throw empty_stack();
        auto res = std::make_shared<T>(data_.top());
        data_.pop();
        return res;
    }
    bool empty() const { std::lock_guard<std::mutex> g(m_); return data_.empty(); }
};
```

`pop()` возвращает `shared_ptr` — один атомарный шаг под блокировкой, гонка
top/pop невозможна. Пустой стек — исключение, а не UB.

#### Листинг 3.6. Обмен двух объектов без deadlock

```cpp
friend void swap(X& lhs, X& rhs) {
    if (&lhs == &rhs) return;
    std::scoped_lock guard(lhs.m, rhs.m);   // блокирует оба мьютекса
    swap(lhs.detail_, rhs.detail_);
}
```

### Типичные ошибки

**Прямые `lock()`/`unlock()` без RAII** — при исключении разблокировки не
произойдёт, остальные потоки зависнут. Всегда `lock_guard`/`unique_lock`/
`scoped_lock`.

**Вернул ссылку/указатель на защищённые данные** — защита рушится: любой код
с этой ссылкой обращается к данным без мьютекса. Не выпускай ссылки за пределы
блокировки.

**Раздельные `empty()`+`top()`+`pop()`** — интерфейсная гонка. Проектируй
единую операцию, которая читает и удаляет под одной блокировкой.

**Блокировка двух мьютексов в разном порядке** — deadlock. Используй
`std::lock`/`std::scoped_lock` или жёсткий единый порядок.

**Double-checked locking** — чтение указателя без блокировки перед проверкой —
это data race. Не оптимизируй вручную; используй `std::call_once` или `static`.

**Держишь мьютекс во время долгих операций (ввод-вывод, вычисления)** —
остальные потоки ждут. Снимай блокировку, как только данные прочитаны/записаны.

### Шпаргалка

| Что | Как | Смысл |
|-----|-----|-------|
| Мьютекс | `std::mutex m;` | примитив взаимного исключения |
| RAII-блокировка | `std::lock_guard<std::mutex> g(m);` | блокирует в ctor, разблокирует в dtor |
| Несколько мьютексов | `std::scoped_lock g(m1, m2, ...);` | блокирует все без deadlock (C++17) |
| Гибкая блокировка | `std::unique_lock<std::mutex> l(m, std::defer_lock);` | отложенная/снимаемая блокировка, `owns_lock()` |
| Рекурсивный мьютекс | `std::recursive_mutex` | повторная блокировка тем же потоком (сигнал плохой конструкции) |
| Общая блокировка | `std::shared_lock<std::shared_mutex> l(m);` | несколько читателей одновременно |
| Чтение-запись | `std::shared_mutex` | много читателей, один писатель |
| Однократная инициализация | `std::call_once(flag, fn)` / `static` | потокобезопасный lazy init |
| Исключение пустоты | `throw empty_stack();` | безопасная реакция на пустой контейнер |
| Возврат из pop | `std::shared_ptr<T>` | единый шаг чтение+удаление, без гонки |
