# Грабли 3.3

## Два отдельных lock_guard вместо scoped_lock

`lock_guard(lhs.m_)` + `lock_guard(rhs.m_)` блокируют мьютексы по очереди. Между
двумя блокировками другой поток успевает захватить второй мьютекст — получается
взаимная блокировка. Нужен `std::scoped_lock` (или `std::lock` + `adopt_lock`),
который блокирует группу атомарно.

## Забыл проверку `&lhs == &rhs`

Если `swap` вызывается с одним и тем же объектом (`swap(x, x)`), `scoped_lock`
попытается заблокировать один мьютекс дважды — для `std::mutex` это UB.
Проверка идентичности обязательна.

## Думаешь, что порядок аргументов не важен

Именно разный порядок (`swap(a,b)` и `swap(b,a)`) создаёт deadlock. Если все
потоки вызывают swap в одном порядке, блокировки совместимы — но полагаться
на это нельзя.

## Считаешь, что TSan поймает deadlock

Нет. Deadlock — не data race и не UB, это состояние ожидания. TSan его не видит.
Проверяется зависанием: если программа не завершается за разумное время — дедлок.
В CI для этого стоит `timeout`.

## Пытаешься решить через recursive_mutex

`recursive_mutex` не решает deadlock: он позволяет одному потоку блокировать
тот же мьютекс несколько раз, но между двумя разными потоками и двумя разными
мьютексами он бессилен. Правильное решение — `scoped_lock`/`std::lock`.
