# Решение 3.3

## В чём баг

Классический deadlock при блокировке двух мьютексов в разном порядке:

```cpp
// плохо:
std::lock_guard<std::mutex> lock_a(lhs.m_);
std::lock_guard<std::mutex> lock_b(rhs.m_);
```

Два потока:
- поток 1: `swap(a, b)` — блокирует `a.m_`, затем пытается `b.m_`;
- поток 2: `swap(b, a)` — блокирует `b.m_`, затем пытается `a.m_`.

Каждый держит один мьютекс и ждёт второй — ни один не продолжается. Deadlock.

## Как чиним — std::scoped_lock

```cpp
std::scoped_lock guard(lhs.m_, rhs.m_);
```

`std::scoped_lock` (C++17) блокирует все переданные мьютексы тем же алгоритмом,
что и `std::lock`: он никогда не оставляет поток в состоянии «один мьютекс
захвачен, второй жду». Если какой-то мьютекс недоступен, уже захваченные
разблокируются, и поток ждёт всю группу целиком. Поэтому две операции swap
с переставленными аргументами не могут взаимно заблокироваться.

Проверка `&lhs == &rhs` обязательна до блокировки: повторная блокировка одного
и того же `std::mutex` тем же потоком — UB (для этого нужен `recursive_mutex`).

## Почему scoped_lock, а не два lock_guard

Два отдельных `lock_guard` блокируют мьютексы последовательно — между первой
и второй блокировкой другой поток может захватить второй мьютекс и создать
цикл ожидания. `scoped_lock` блокирует «одновременно» (атомарно для группы),
что исключает этот цикл.

## Проверка

- Хорошая версия (со `scoped_lock`): программа завершается быстро, вывод
  `a=... b=...`, exit 0.
- Плохая версия (две `lock_guard`): программа зависает — `timeout 5` убивает её
  по таймауту. (Deadlock — не data race, TSan его не ловит; проверяется
  именно отсутствием зависания.)
