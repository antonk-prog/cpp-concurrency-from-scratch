# Модуль 3 — Совместное использование данных несколькими потоками — ПЛАН

## Допущения модуля

### Прогрессия (что разрешено)
Всё из главы 3:
- `std::mutex`, `std::recursive_mutex`, `std::shared_mutex` (C++17).
- RAII-обёртки: `std::lock_guard`, `std::scoped_lock` (C++17), `std::unique_lock`,
  `std::shared_lock`, `std::adopt_lock`, `std::defer_lock`.
- `std::lock()` — одновременная блокировка нескольких мьютексов без deadlock.
- `std::once_flag`, `std::call_once`; thread-safe lazy init через `static local`.
- Паттерны: защита данных в классе, интерфейсные гонки, передача владения
  блокировкой (unique_lock), степень детализации блокировки.
- `std::stack`, `std::shared_ptr` для потокобезопасного стека (глава 3).

Запрещено (позднее): условные переменные, фьючерсы/промисы (гл. 4),
атомики/ordering (гл. 5), структуры данных гл. 6–7.

### Последствие для лаб
Лабы строятся вокруг защиты разделяемых данных мьютексами: безопасные
классы-контейнеры (стек), исправление интерфейсных гонок, deadlock и его
решение. Для «найди и почини» — закладываем реальные гонки, которые TSan ловит.

### Список лаб (тип, название, суть, чему учит)

1. **lab-03-01-guarded-counter (напиши с нуля, базовая)**
   - Суть: класс `Counter` с мьютексом и lock_guard; несколько потоков
     инкрементируют общий счётчик. Показать, что без мьютекса гонка, с мьютексом —
     корректный итог.
   - Чему учит: RAII-защита разделяемых данных, lock_guard, почему мьютекс —
     не панацея без структурирования кода (данные+мьютекс в одном классе).

2. **lab-03-02-interface-race (найди и почини, средняя)**
   - Суть: дан «потокобезопасный» стек с интерфейсом top()/pop()/empty()
     (раздельные вызовы) — интерфейсная гонка; исправить интерфейс
     (единая операция pop, возвращающая shared_ptr / значение).
   - Чему учит: состояние гонки, присущее интерфейсу; проектирование безопасного
     интерфейса потокобезопасного стека.

3. **lab-03-03-deadlock-swap (допиши TODO, сложная)**
   - Суть: класс с двумя мьютексами, операция обмена; в стартовом коде — взаимная
     блокировка при обмене двумя объектами из разных потоков; дописать правильную
     блокировку через `std::scoped_lock` (или `std::lock` + adopt_lock).
   - Чему учит: deadlock и его причины; `std::lock`/`std::scoped_lock`; порядок
     блокировок.

> В лабах 3.2/3.3 используем shared_ptr/unique_ptr-попадание в интерфейс —
> это в рамках главы 3 (варианты pop из листинга 3.4).

## Заголовки лекции (README.md) с 1–2 фразами содержания

1. **Зачем это нужно** — что такое состояние гонки и нарушение инвариантов; почему
   общие изменяемые данные без защиты — источник UB; как мьютекс это решает.

2. **Как это работает** — std::mutex + lock_guard (RAII); защита через класс;
   почему нельзя возвращать ссылки на защищённые данные; интерфейсные гонки
   (top/pop/empty); deadlock и std::lock/scoped_lock; unique_lock и передача
   владения; детализация блокировки.

3. **Минимальные примеры** — счётчик под lock_guard; потокобезопасный стек;
   обмен двумя объектами через scoped_lock; call_once для ленивой инициализации;
   shared_mutex для редко обновляемых данных.

4. **Типичные ошибки** — забыл lock_guard (прямой lock/unlock); вернул ссылку
   на защищённые данные; раздельные top()+pop(); deadlock при блокировке в разном
   порядке; double-checked locking; блокировка на время долгой операции.

5. **Шпаргалка** — таблица: mutex, lock_guard, scoped_lock, unique_lock,
   shared_lock, shared_mutex, std::lock, call_once/once_flag, adopt_lock/defer_lock,
   recursive_mutex.
