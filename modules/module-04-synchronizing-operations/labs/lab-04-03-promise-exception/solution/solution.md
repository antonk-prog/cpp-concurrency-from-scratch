# Решение 4.3

Два дефекта и их исправление.

## Дефект 1 — гонка за буфер (порядок записи и сигнала)

```cpp
// было (плохо):
ready.set_value();          // сигнал раньше данных
compute_data(buffer);       // данные после сигнала

// стало (правильно):
compute_data(buffer);       // сначала данные
ready.set_value();          // потом сигнал
```

Почему порядок критичен: вызов `promise.set_value()` синхронизируется с
`future.get()` в потребителе (отношение happens-before). Это значит, что все
записи поставщика, сделанные **до** `set_value()`, гарантированно видны
потребителю после возврата из `get()`. А вот запись, сделанная **после**
`set_value()`, никак не упорядочена относительно чтения потребителя: он может
прочитать буфер, пока поставщик ещё пишет, — это data race / UB.

## Дефект 2 — потерянный сигнал при исключении (broken_promise)

```cpp
// было (плохо):
try {
    ...
} catch (...) {
    // promise не установлен → при уничтожении = broken_promise
}

// стало (правильно):
try {
    compute_data(buffer);
    ready.set_value();
} catch (...) {
    ready.set_exception(std::current_exception());
}
```

Промис — это «обязательство» предоставить значение или исключение. Если промис
уничтожается, не установив ничего, во фьючерс сохраняется `std::future_error`
с кодом `broken_promise`, и ожидающий поток получает исключение, а не результат.
`set_exception(std::current_exception())` кладёт во фьючерс текущее исключение —
`get()` в потребителе повторно бросит его, и программа корректно сообщит об
ошибке вместо загадочного `broken_promise`.

## Итог

Потребитель вызывает `future.get()` и после возврата читает `buffer`. Так как
буфер заполнен до `set_value()`, а `set_value` синхронизируется с `get()`, все
данные гарантированно видимы и корректны — программа печатает `OK` и завершается
кодом 0. TSan чист: одновременных обращений к `buffer` без синхронизации нет.
