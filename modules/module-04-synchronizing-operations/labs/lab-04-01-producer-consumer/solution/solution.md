# Решение 4.1

Три метода потокобезопасной очереди.

## push

```cpp
void push(int value) {
    {
        std::lock_guard<std::mutex> lk(mut_);
        data_queue_.push(value);
    }
    data_cond_.notify_one();   // после разблокировки мьютекса
}
```

Значение кладётся в очередь под `lock_guard`. Уведомление вызывается **после**
выхода из области блокировки: разбуженный потребитель немедленно сможет
захватить мьютекс, а не конкурировать с производителем за него. (Если бы
`notify_one` шёл при захваченном мьютексе, разбуженный поток сначала попытался
бы взять блокировку, не смог и снова уснул бы.)

## wait_and_pop

```cpp
void wait_and_pop(int& value) {
    std::unique_lock<std::mutex> lk(mut_);
    data_cond_.wait(lk, [this] { return !data_queue_.empty(); });
    value = data_queue_.front();
    data_queue_.pop();
}
```

Ключевые моменты:

- **`unique_lock`, а не `lock_guard`.** `wait` снимает блокировку, пока поток
  спит, и снова захватывает после пробуждения. `lock_guard` не умеет снимать
  и забирать мьютекс — с ним `wait` даже не скомпилируется.
- **Предикат обязателен.** `wait(lk, pred)` эквивалентен циклу
  «пока !pred — разблокировать, ждать, заблокировать». Он защищает от ложных
  пробуждений (spurious wakeup): даже если поток разбудили без уведомления или
  очередь снова опустела, он продолжит ждать, пока условие не выполнится.
- После `wait` мьютекс снова захвачен — можно безопасно читать `front()`.

## try_pop

```cpp
bool try_pop(int& value) {
    std::lock_guard<std::mutex> lk(mut_);
    if (data_queue_.empty()) return false;
    value = data_queue_.front();
    data_queue_.pop();
    return true;
}
```

Неблокирующая альтернатива: вернуть `false`, если данных нет, — без ожидания
и без исключений. Для `try_pop` хватает `lock_guard`: поток не уходит в сон.

## Почему сумма сходится

Продюсер кладёт ровно `n` значений и на каждом `push` делает `notify_one()`.
Потребитель ровно `n` раз вызывает `wait_and_pop`: на каждом значении он либо
застаёт очередь непустой (предикат сразу `true`), либо засыпает и просыпается
по уведомлению. Так как уведомления не теряются между «положили в очередь» и
«заснули» (условие проверяется предикатом), все `n` значений будут извлечены
и сумма составит 1 + 2 + ... + 100 = 5050.

## Вывод

```
Sum = 5050
```

TSan на решении чист: к очереди обращаются только под мьютексом, `sum` пишет
только потребитель, а читает главный поток после `join()` (создаёт
happens-before).
