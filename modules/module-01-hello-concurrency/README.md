# Модуль 1. Здравствуй, мир конкурентности в C++!

## Лекция

### Зачем это нужно

Конкурентность (concurrency) — это выполнение двух и более отдельных задач
«одновременно»: пока одна часть программы считает данные, другая — рисует
интерфейс, третья — ждёт ответа сети. Без неё пришлось бы делать всё строго
по очереди, а это не всегда приемлемо.

Практически все причины использовать конкурентность сводятся к двум:

1. **Разделение неотложных задач.** Функционально разные обязанности программы
   разносим по отдельным потокам, чтобы они не мешали друг другу. Классика —
   приложение с UI и тяжёлой обработкой данных: поток интерфейса мгновенно
   реагирует на клики, пока рабочий поток что-то долго считает. Число потоков
   здесь не зависит от числа ядер — важно лишь логическое разделение обязанностей.

2. **Повышение производительности.** Делим работу между доступными ядрами,
   чтобы использовать оборудование. Два способа:
   - **Параллелизм задач** — одну задачу режем на независимые части и считаем их
     параллельно, сокращая общее время.
   - **Параллелизм данных** — одна и та же операция применяется к разным наборам
     данных (например, обрабатываем одновременно не один файл, а двадцать).

   Тут число потоков напрямую связано с числом ядер.

Но конкурентность — не бесплатный обед. Есть и случаи, когда она **не нужна**:
запуск потока стоит времени и ресурсов (поток требует собственного стека
и системных структур), потоки — ограниченный ресурс, а чем их больше, тем больше
переключений контекста делает операционная система. **Переключение контекста** —
это сохранение состояния одного потока (значения регистров, счётчик команд)
и загрузка состояния другого, прежде чем он продолжит выполняться; на это
тратится время процессора. Если задача микроскопическая,
издержки на создание потока могут перевесить выгоду. Если же выигрыш в скорости
невелик или задачи плохо делятся, усложнение кода и рост числа ошибок не окупаются.
Конкурентность оправдана там, где выгода ощутима, — применять её стоит осознанно.

### Как это работает

Есть два принципиально разных подхода к конкурентности в приложении.

**Несколько процессов.** Каждый процесс — изолированная программа со своим
адресным пространством. Обмениваются они через механизмы IPC (от англ.
inter-process communication — межпроцессное взаимодействие: сокеты, файлы,
конвейеры, сигналы). Плюс: изоляция — один процесс не может случайно испортить
данные другого. Минусы: запуск процесса дорог, а обмен данными медленный
и сложный (нужны защитные меры ОС). Зато процессы можно раскидать по разным
машинам в сети.

**Несколько потоков в одном процессе.** Потоки — «облегчённые процессы»:
каждый выполняет свою последовательность инструкций независимо, но все они
живут в **одном адресном пространстве** и потому свободно читают и пишут общие
данные. Это дёшево и удобно, но даёт и главную ответственность: если несколько
потоков одновременно трогают одни и те же данные, программист обязан
синхронизировать доступ — иначе получаем гонку (data race). О том, как это
делать, — главы 3–5.

Стандарт C++ не даёт встроенной поддержки обмена данными между процессами
(там приходится звать платформенные API). Поэтому весь курс — про потоки,
и дальше под «конкурентностью» мы будем понимать именно многопоточность.

Термины «конкурентность» и «параллелизм» часто путают. Формально параллелизм
сильнее подчёркивает использование оборудования для производительности, а
конкурентность — разделение задач и отзывчивость. На практике они во многом
пересекаются, и в курсе встретятся оба.

**История поддержки в C++.** В стандарте C++98 потоков не было вовсе — действия
языка описывались для последовательной абстрактной машины, а модель памяти
не была определена. Многопоточность достигалась платформенными расширениями
(API C, библиотеки вроде Boost и ACE). Всё изменил **C++11**: появилась модель
памяти и стандартная библиотека потоков (`<thread>` и другие заголовки).
C++14 добавил один тип мьютекса, а C++17 — параллельные алгоритмы. Эта история
важна: многие решения библиотеки потоков унаследованы от Boost и отзываются
привычным API. Мы работаем в C++17.

### Минимальные примеры

Обычная программа в один поток:

```cpp
#include <iostream>

int main() {
    std::cout << "Hello World\n";
}
```

Теперь тот же вывод, но в отдельном потоке:

```cpp
#include <iostream>
#include <thread>

void hello() {
    std::cout << "Hello Concurrent World\n";
}

int main() {
    std::thread t(hello);   // запускает новый поток, который начинает с hello()
    t.join();               // main ждёт завершения потока t
}
```

Три отличия от однопоточной версии:

1. `#include <thread>` — здесь объявлены классы и функции управления потоками.
2. Код вынесен в функцию `hello()` — у каждого потока есть **исходная функция**,
   с которой начинается его выполнение. Для главного потока это `main()`,
   для остальных — функция, переданная в конструктор `std::thread`.
3. Появился `join()` — он заставляет вызвавший поток (здесь `main`) ждать
   завершения потока, связанного с объектом `t`.

Зачем нужен `join()`? После запуска нового потока исходный продолжает работать
сам по себе. Если бы `main` не ждал, он дошёл бы до конца и завершил программу,
возможно, раньше, чем новый поток успел бы вывести строку. `join()` — простейший
способ гарантировать, что фоновый поток успел закончить работу.

Ещё полезная функция — узнать идентификатор текущего потока:

```cpp
#include <iostream>
#include <thread>

int main() {
    std::cout << "Главный поток: " << std::this_thread::get_id() << "\n";
    std::thread t([] {
        std::cout << "Рабочий поток: " << std::this_thread::get_id() << "\n";
    });
    t.join();
}
```

Здесь мы воспользовались лямбдой как исходной функцией потока — это удобно,
когда логика короткая. Управление потоками — передачу аргументов,
`join`/`detach`, владение потоком и число потоков — подробно разберём
в модуле 2.

### Передача аргументов в поток

Конструктор `std::thread` не только выбирает исходную функцию, но и передаёт
ей аргументы: всё, что перечислено после имени функции, попадает в неё как
параметры.

```cpp
#include <iostream>
#include <thread>

void printNumber(int x) {
    std::cout << x << "\n";
}

int main() {
    std::thread t(printNumber, 42);  // вызовет printNumber(42)
    t.join();
}
```

Под капотом это устроено так: конструктор `std::thread` **копирует** переданные
аргументы в хранилище, принадлежащее новому потоку, а затем вызывает функцию
уже с этими копиями — тип параметра функции на копирование не влияет. Из этого
следует важное следствие: если функция ждёт ссылку (`int&`) и хочет изменить
переменную из `main`, копия не подойдёт — поток обновил бы собственную копию,
а оригинал остался бы прежним. Чтобы передать настоящую ссылку, оберни аргумент
в `std::ref`:

```cpp
#include <iostream>
#include <thread>

void computeSum(int n, int& sum) {
    sum = 0;
    for (int i = 1; i <= n; ++i) {
        sum += i;
    }
}

int main() {
    int sum = 0;
    std::thread t(computeSum, 100, std::ref(sum));
    t.join();
    std::cout << sum << "\n";   // 5050 — sum изменился в main
}
```

`std::ref(x)` создаёт обёртку ссылки, которая безопасно копируется в поток,
а внутри функции разыменовывается в настоящую ссылку на `x`. Механику передачи
аргументов (включая move-only типы и ловушку с указателями) подробно разберём
в модуле 2, но базовый приём понадобится уже в лабе 1.1.

### Типичные ошибки

**Забыл `join()` или `detach()`.** У каждого `std::thread` обязан быть вызван
либо `join()`, либо `detach()`, прежде чем объект будет разрушен. Если поток
всё ещё joinable (ни то, ни другое не вызвано), а объект уничтожается, — программа
падает через `std::terminate()`. `std::terminate()` — это аварийное завершение
программы: стандартная библиотека вызывает его в ситуациях, которые не может
разрешить (например, уничтожение ещё запущенного `std::thread`). В модуле 2 мы
сделаем RAII-обёртку, которая гарантирует join даже при исключении; пока просто
помни про обязательность.

**Думаешь, что порядок вывода предсказуем.** Потоки выполняются конкурентно,
и их относительный порядок не гарантирован. Если два потока пишут в один
`std::cout`, результат может перемешаться или зависеть от планировщика. В этом
модуле мы избегаем такой ситуации, а защиту общего вывода разберём в главе 3.

**Ждёшь, что detach-поток успеет отработать.** `detach()` отсоединяет поток —
он продолжает жить сам по себе, а управляющий объект `std::thread` больше с ним
не связан. При завершении `main` программа заканчивается, и фоновый поток может
не успеть ничего сделать. Это не ошибка сама по себе, но часто становится
неожиданностью.

### Шпаргалка

| Что | Как | Смысл |
|-----|-----|-------|
| Запуск потока | `std::thread t(функция, аргументы...)` | создаёт и запускает поток с исходной функцией |
| Ссылка в аргументе | `std::ref(x)` | передать настоящую ссылку сквозь копирование аргументов |
| Ожидание | `t.join()` | ждёт завершения потока `t` |
| Отсоединение | `t.detach()` | поток живёт независимо, объект разрывает связь |
| Проверка | `t.joinable()` | true, если join/detach ещё не вызван |
| Текущий поток | `std::this_thread::get_id()` | идентификатор текущего потока |
| Число ядер | `std::thread::hardware_concurrency()` | подсказка о числе аппаратных потоков |
| Идентификация | `t.get_id()` | идентификатор потока объекта `t` |
