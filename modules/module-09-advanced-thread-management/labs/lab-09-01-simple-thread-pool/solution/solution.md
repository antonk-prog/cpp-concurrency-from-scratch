# Решение лабы 9.1

## Реализация

Пул из трёх частей: очередь задач, рабочие потоки и корректное завершение.

**Очередь и флаг** — объявлены ДО вектора потоков, вектор — ДО `join_threads`.
При разрушении объекта поля уничтожаются в обратном порядке: сначала
`join_threads` присоединит все потоки, потом разрушится вектор `std::thread`,
и только потом — очередь и флаг. Если бы очередь шла раньше, она могла бы
разрушиться, пока рабочие потоки ещё её используют.

**`worker_thread()`** — цикл, пока `!done`:

```cpp
void worker_thread() {
    while (!done) {
        std::function<void()> task;
        if (work_queue.try_pop(task)) {
            task();
        } else {
            std::this_thread::yield();
        }
    }
}
```

`try_pop` не блокирует: если задач нет, поток уступает процессор (`yield`),
чтобы другие потоки могли добавить работу. Поток завершается, когда видит
`done = true`.

**Конструктор** — `hardware_concurrency()` потоков. Если запуск потока
провалился (исключение), `done = true` и `throw` — уже запущенные потоки
завершатся, а исключение уйдёт дальше. `join_threads` в этом случае тоже
отработает, потому что он уже сконструирован.

**`submit(f)`** — упаковывает задачу в `std::function<void()>` и кладёт в
очередь. Потокобезопасность очереди обеспечивает `thread_safe_queue`.

## Почему `yield`, а не ожидание

Простой пул не умеет ждать завершения задач: рабочий поток, упёршись в
пустую очередь, просто уступает процессор и пробует снова. `yield` дёшев и
даёт другим потокам возможность положить работу. (Блокирующее ожидание на
условной переменной — тоже вариант, но тогда завершение пула потребует
уведомления всех потоков.)

## Проверка

`main` отправляет 20 000 задач, каждая увеличивает атомарный счётчик и
накапливает сумму. Так как пул не возвращает результатов, `main` опрашивает
счётчик с предохранителем от бесконечного ожидания. Все задачи выполнены
ровно по одному разу, сумма верна — `result = OK`, exit 0. TSan чист:
очередь защищена мьютексом, счётчики атомарны.
