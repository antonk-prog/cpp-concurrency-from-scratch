# Грабли лабы 5.4

## Поставил барьер освобождения после ready.store()

Барьер обязан стоять **до** публикации готовности: он «выталкивает» записи
`data`, которые иначе могли бы оказаться позже флага. Если поставить барьер
после `ready.store()`, читатель может увидеть `ready == true`, а данные —
ещё нет.

## Поставил барьер захвата до ожидания готовности

Барьер захвата должен стоять **после** того, как читатель увидел
`ready == true`. Если поставить его раньше, он не свяжется с release-барьером
писателя, и упорядочения не будет.

## Заменил флаг на обычный bool

Флаг обязан оставаться атомарным (`std::atomic<bool>`): чтение/запись обычного
`bool` из двух потоков — гонка за данные, даже с барьерами вокруг.

## Пытался «синхронизироваться» через sleep_for

`sleep_for` не создаёт упорядочения. Корректно — цикл ожидания с `yield()`
и правильные барьеры.

## Не проверил корректность рассуждением

TSan не поддерживает `std::atomic_thread_fence` (игнорирует барьеры, а на
корректном решении с неатомарными данными может выдать **ложную** гонку).
Полагайся не только на TSan: аргументируй пару release/acquire барьеров
и прогоняй программу многократно. А вот стартер без барьеров TSan ловит
честно — там гонка реальная.
