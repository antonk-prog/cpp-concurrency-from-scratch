# Решение лабы 5.5

## Реализация

Писатель создаёт объект в куче и публикует указатель с `release`:

```cpp
void producer() {
    Payload* p = new Payload{kExpectedId, kExpectedText};
    published.store(p, std::memory_order_release);
}
```

Читатель ждёт непустой указатель загрузкой с `acquire` и проверяет поля:

```cpp
void consumer(bool* ok) {
    Payload* p = nullptr;
    while ((p = published.load(std::memory_order_acquire)) == nullptr) {
        std::this_thread::yield();
    }
    *ok = (p->id == kExpectedId && p->text == kExpectedText);
}
```

## Почему это корректно

Пара `store(release)` → `load(acquire)` над одной переменной `published`
устанавливает отношение «синхронизируется с»: читатель, увидевший указатель,
гарантированно увидит и **все записи**, сделанные писателем до публикации —
то есть поля `Payload`. Объект не может «полусобранным» попасть в руки
читателя.

## Почему acquire, а не consume

Загрузка полей `p->id` и `p->text` формально зависит от прочитанного указателя
— то есть хватило бы и `consume`. Но на практике `consume` в C++17 почти не
реализуется компиляторами, стандарт рекомендует `acquire`, поэтому в задаче
используется именно он. Цена — чуть меньше свободы оптимизаций, зато код
переносимый.

## Почему один release хватает для четырёх читателей

Каждый из четырёх читателей делает свою `load(acquire)` на `published`.
Любая из них, увидевшая опубликованное значение, синхронизируется с тем же
`store(release)`. Один писатель может раздать объект сколь угодно многим
читателям.

## Проверка

- Все четыре читателя возвращают `true`; программа печатает `OK`.
- TSan чист: гонки за `published` и за поля `Payload` нет.
