# Решение лабы 5.3

## Реализация

Ключевой приём — **CAS-цикл**: инкремент/декремент выполняются не готовым
атомарным оператором, а через `compare_exchange_weak` в цикле.

```cpp
void increment() {
    int expected = value_.load();
    while (!value_.compare_exchange_weak(expected, expected + 1)) {
        // expected обновлён; пробуем снова
    }
}
```

## Почему это корректно

`compare_exchange_weak(expected, desired)` атомарно делает следующее:
сравнивает текущее значение с `expected`; если равны — записывает `desired`
и возвращает `true`; если нет — записывает в `expected` актуальное значение
и возвращает `false`.

Возможны два сценария неудачи в цикле:

1. **Другой поток изменил счётчик** между `load()` и `CAS`. Тогда сравнение
   не сходится, `expected` обновляется до актуального значения, и цикл повторяет
   попытку уже с новым `expected`. Значение не теряется: каждый поток «дожимает»
   свою операцию до успеха.
2. **Ложный сбой** `compare_exchange_weak`. Даже если значения совпадали,
   `weak` может вернуть `false` (например, на архитектурах без единой инструкции
   CAS). `expected` при этом остаётся прежним, и цикл просто пробует ещё раз.
   Это безопасно: данные не повреждаются, операция повторяется.

Именно поэтому `weak` удобен в цикле: он может «дешево» провалиться, но цикл
это переживает. `compare_exchange_strong` гарантирует `false` только при реальном
несовпадении — здесь он не обязателен и был бы избыточен.

## Почему используется seq_cst

По умолчанию все атомарные операции используют `memory_order_seq_cst` —
самый строгий порядок. Для этого счётчика достаточно и `relaxed` (каждая операция
независима, между ними нет передачи данных), но `seq_cst` проще и на x86 почти
не дороже. В реальном коде счётчик вроде этого обычно делают `relaxed`.

## Проверка

Финальное значение равно 0, потому что каждое `increment()` скомпенсировано
`decrement()` тем же потоком, а CAS-цикл гарантирует атомарность каждого шага.
При 8 потоках × 100000 итераций счётчик всегда сходится к 0; TSan чист.

## Куда это ведёт

Такой же CAS-цикл лежит в основе операций, для которых нет готового атомарного
оператора (умножение, сдвиг, сложные обновления структуры) и структур данных
без блокировок (глава 7). А когда CAS-цепочка используется для синхронизации
нескольких потребителей (как в листинге 5.11), на помощь приходят
последовательности освобождений (release sequences).
