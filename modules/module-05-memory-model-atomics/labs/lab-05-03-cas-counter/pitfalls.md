# Грабли лабы 5.3

## Не перезагрузил `expected` на каждом проходе цикла

Если не перечитывать/не использовать обновлённый `expected`, CAS будет
бесконечно сравнивать со старым значением, которое уже никто не может совпасть —
бесконечный цикл. `expected` обязан обновляться (это делает сама неудачная
попытка CAS) и использоваться в новой попытке.

## Использовал `compare_exchange_strong` без необходимости

`strong` в цикле работает, но на платформах без аппаратного CAS он реализован
через внутренний цикл — получается «двойной» цикл и лишние пересчёты желаемого
значения. В цикле достаточно `weak`, который на таких платформах быстрее.

## Использовал `fetch_add` / `++` вместо CAS

Задача явно запрещает `fetch_add`, `fetch_sub`, `++`, `--`, `+=`, `-=` — смысл
в том, чтобы научиться писать CAS-цикл вручную. Он нужен там, где готового
атомарного оператора нет (например, `fetch_mul` не существует).

## Считал, что CAS сам по себе «вычисляет» новое значение

CAS только сравнивает и записывает. Желаемое значение (expected ± 1) ты обязан
вычислить сам между `load()` и `CAS`. Ошибка тут — вычислить `desired` один раз
до цикла и не пересчитывать при неудаче: тогда после чужого изменения предложишь
неверное значение. (Хотя в нашем случае `expected + 1` корректно, потому что
`expected` перезагружается.)

## Не проверил гонку

Даже «правильный на глаз» CAS-код может содержать гонку. Прогони
`-fsanitize=thread`: решение должно быть чистым. И убедись, что финальное
значение стабильно сходится к 0 при многократных запусках.
