# Решение лабы 5.6

## Реализация

Писатель заполняет массив и публикует счётчик с `release`:

```cpp
void publish() {
    for (int i = 0; i < kCount; ++i) items[i] = i * 2;
    count.store(kCount, std::memory_order_release);
}
```

Потребитель забирает элемент через `fetch_sub` с `acquire`:

```cpp
int claim() {
    return count.fetch_sub(1, std::memory_order_acquire);
}
```

## Почему это корректно

Первый потребитель, чей `fetch_sub(acquire)` прочитал значение, записанное
`count.store(release)`, синхронизируется с писателем: он видит `items`.

Второй и последующие потребители читают значение, записанное **не самим**
`store`, а предыдущим `fetch_sub`. «Наивно» кажется, что синхронизации
с писателем у них нет. Но цепочка операций чтения-изменения-записи над `count`
образует **release sequence**: начальное `store(release)` синхронизируется
с финальной загрузкой даже через промежуточные `fetch_sub`. Поэтому все
потребители гарантированно видят `items`, независимо от порядка, в котором
они забирали элементы.

## Почему каждый элемент обработан ровно один раз

`fetch_sub` атомарен: каждое значение `50, 49, …, 1` выдаётся ровно одному
потребителю. Значит, индекс `v - 1` уникален, и `processed[idx]` пишется
одним потоком. Когда счётчик уходит в `0` и ниже, все `v <= 0` —
потребители останавливаются.

## Проверка

- Программа печатает `OK`; все 50 элементов обработаны.
- TSan чист: гонки за `items` нет именно благодаря release sequence.
  Если бы `count.store` был `relaxed` (или данные писались после публикации),
  TSan поймал бы гонку за `items`.
